# Inline Disassembly - Decisions (Q&A)

Decisions for integrating inline disassembly (and composing it with unified diff and per-line numbering) into the pipeline described in [text-tokenization-pipeline.md](text-tokenization-pipeline.md).

Status: **implemented (v1, complete)** — every question is marked **DECIDED** inline (with rationale and consequences) and the resulting design is implemented and working end-to-end. This file kept its original `inline-disasm-open-questions.md` name and URL for link stability, but it is **no longer an open-questions / triage doc**: the questions are settled and this is the source of truth for the inline-disassembly work.

## Implementation (v1) — where the decisions landed

- **Model** (`demo-edit`): a nullable `Document.sourceToDoc` mapping plus `srcStart` and `maxLineNumber`, built once at creation by `Document.fromDescriptors(...)` from the descriptor ordinals; the per-line number lives on `CodeLine.lineNumber` (`0` = AUTO in a classic document / attached in a mapped one). Every `Document` mutation is hard-blocked while `sourceToDoc != null` (`Document.rejectMappedEdit`). — `Document`, `CodeLine`
- **Parser / viewport**: `ParserUtils.updateDocument` / `updateDocumentInterval` scatter parser output through `sourceToDoc` (preserving `lineNumber`); `Model.parseViewport` translates the visible document range into a source range by binary search and `parsedVps` stores the covered **source** intervals; `Model.setSemanticToken` and `Document.onResolve` work in source space and colour **source lines only**. — `ParserUtils`, `Model`, `Document`
- **Rendering**: the gutter is driven by a number-addressed lookup (`EditorComponent` + `LineNumbersTexture`); attached disassembly lines render unnumbered. — `EditorComponent`, `LineNumbersComponent`, `LineNumbersTexture`
- **Read-only**: `EditorComponent.editsBlocked()` blocks every modifying operation when `sourceToDoc != null`; `readonly` is the UI mirror set at attach, with a warn-once fallback (Q9).
- **JS API**: `newTextModelFromLines(workers, lines, language?, uri?)` over `ILineDescriptor` (`{ lineNumber?, content }`, declared in `common-ts-types/frontend.d.ts`); Java side is `JsTextModel` / `JsLineDescriptor`. — `common-editor-js`, `code-review-module`
- **Sample**: `code-review-module/module/samples/inlineDisasm.js` + `.html`.
- **Tests**: `DocumentTest`, `ParserUtilsMappedTest`, `CodeLineTest`.

Still explicitly **deferred / TBD** (none blocking v1): **Q13** disassembly color scheme; **Q2** lazy add/replace after creation; **Q16** folding for disassembly documents. Unified diff (**Q17-Q18**) remains a later, separate view-level step and does not compose with inline disassembly in v1.

## A. Model and ownership

### 1. Where do disassembly lines live? — DECIDED (a)

**Decision:** Variant **(a)** - disassembly lines are `CodeLine`s **in the same `Document.lines`**, interleaved with source lines. (Implemented in v1.)

**Context:** Earlier decision says disassembly lines are `CodeLine`s in the same `Document` (so view order is document order, and compact mapping includes them).

**Rationale:**
- One document keeps a single view order, so there is no separate interleave layer to build or keep in sync.
- The existing compact/folding mapping already works over document indices, so disassembly lines need no special view mapping.
- Matches the line-numbers refactoring assumption (see [line-numbers-refactoring-QA.md](line-numbers-refactoring-QA.md) Q12: attached disasm lines are `CodeLine`s in the same `Document`, never numbered — `lineNumber == 0`, not members of `sourceToDoc`).

**Consequence:** The parser must receive a **source-only** view; today `document.getChars()` includes everything. This puts **Q4 (source extraction)**, **Q5 (line index mapping)**, and **Q6 (coordinate space)** on the critical path (see section F).

**Alternatives considered (not chosen for now):**
- (b) A distinct "attached lines" layer owned by the view/editor, rendered interleaved but **not** part of the parser document.
- (c) A second `Document` for disassembly, interleaved at view time.

**Status:** Implemented in v1 (variant (a) shipped). Revisit (b)/(c) only if keeping disassembly in the parser document proves too costly.

### 2. Who produces disassembly lines, and when? — DECIDED

**Decision:** Disassembly comes from the **JS API**. A dedicated Java method will create a new document model from an **array of line descriptors**. Each descriptor carries:

- a **line number** — if present, the line is a **source** line;
- the line content — either a **source line** (text) or a **disassembly line**.

The **source index array (Q4/Q5) is built here**, at document creation, from the descriptors that carry a line number. Disassembly is therefore supplied up front by the caller (not generated by a worker/debugger in this design), and the model is constructed in one pass.

**Context:** today nothing in the model generates disassembly.

**Deferred (out of scope for v1):** adding/replacing disassembly lazily after creation is not planned — disassembly documents are built once at creation (Q3/Q9) and read-only; a lazy-add path would reintroduce mapping maintenance (Q5). The index is therefore rebuilt only by recreating the document.

### 3. Lifetime and anchoring of disassembly lines — DECIDED (scope: out of scope for now)

**Decision:** Editing documents that contain disassembly lines is **not** considered at the moment. Therefore there is **no anchoring/lifetime logic** yet: disassembly lines are not moved, deleted, or recomputed in response to edits.

- Consequence: for a disassembly document, the source index buffer (Q4/Q5) is **built once at creation** and not patched.
- Documents **without** disassembly lines are unaffected — they use the identity mapping (see Q4), exactly as today.
- Revisit when editing disassembly documents becomes a goal; the options remain: (a) anchored to a source line, (b) pinned at a position, (c) recomputed on edit.

**Context:** if a source line is edited/deleted, or lines are inserted/removed, what happens to its disassembly lines?

## B. Parser input and coordinate mapping

### 4. How is source extracted for the parser? — DECIDED (a)

**Decision:** Variant **(a)** — maintain a **parallel "source-only" buffer**, but as **indices into the document**, not a copy of the text. The model must **not** send disassembly to the worker.

- The buffer is an array of **document line indices** covering the source lines. Disassembly lines are simply absent from it.
- **No text is duplicated:** the buffer references the existing `document.lines`; it stores positions, not characters.
- **Payload:** when calling the worker, the source `char[]` is **materialized** from the referenced lines (the worker still needs a text payload).
- **Identity shortcut:** when the document has **no disassembly lines**, the buffer is **`null`**, meaning the mapping is the identity (`docLine == sourceLine`). This is the common case, so no array is allocated and no maintenance code runs.
- **Ownership (who writes it):** the nullable `int[] sourceToDoc` lives on **`Document`** (not on `Model`). The **JS descriptor factory** (Q2) is the only writer — it sets the array **once** at document creation from the descriptors. `Model`, `ParserUtils`, the viewport/interaction layers, and `setSemanticTokens` only **consume** it (read-only). No other component patches it, which is what makes the built-once contract (Q3) auditable in one place. Keep `Document.getChars()` (full document text, used by copy — Q11) distinct from the source materialization (the worker payload, materialized from the referenced lines).

**Source of truth for source-ness:** the **source index buffer itself** decides which lines are source — a line is source iff it is present in the index. Numbering coincides with source-ness (Q5 ordinal invariant / line-numbers Q9), and **there is no per-line `hasLineNumber` flag**: numbered ⟺ member; every member carries `lineNumber` = its ordinal, every non-member (attached line) has `lineNumber == 0` and shows nothing.

**Consequence:** This same index buffer is the mapping used to apply the parser response back (Q5), and the worker's positions are in **source space** (Q6).

**Context:** `Model` sends `document.getChars()` to the worker today; with disassembly lines present this must be source-only.

**Alternatives considered (rejected):**
- (b) Build a filtered `char[]` on demand with no persistent index buffer.
- (c) Pass a source-line mask to the worker and let it skip disassembly lines (leaks disassembly into the parser contract).

### 5. Line index mapping (parser <-> document) — DECIDED

**Decision:** Store only the **forward** index array `sourceToDoc` (source line → document line) — this is the **same index buffer as Q4**. It is built at document creation from the line descriptors (Q2); **`null` means the identity mapping** (no disassembly lines, see Q4).

- **`sourceToDoc[i] = documentLine`** for source line `i`. The inverse is **not stored**: for a document line `d`, the source line is simply `document.lines[d].lineNumber` (non-source / disassembly lines carry no line number). A second array would only mirror the model.
- **1-based numbers vs 0-based indices:** line numbers are 1-based (source line 1 has number 1) while the forward array is indexed 0-based; both use the same ordering, so `sourceIndex(d) = document.lines[d].lineNumber - 1`.
- **Ordinal invariant (constrains `lineNumber`):** whenever `sourceToDoc != null`, `lineNumber` is **always the 1-based source ordinal**. The JS API assigns it from the source descriptors (Q2), so it holds structurally. **Display renumbering / arbitrary values are not supported in a disassembly document** — the "arbitrary display number" freedom in [line-numbers-refactoring-QA.md](line-numbers-refactoring-QA.md) Q5 applies only to documents with `sourceToDoc == null` (identity), whose reverse mapping is identity and never consults `lineNumber`. **`lineNumber == 0` (AUTO) is not valid on numbered lines here:** in a classic document (`sourceToDoc == null`) `0` means *derive the natural ordinal* (line-numbers QA Q9); in a disassembly document such a derivation would yield *document* order, not the source ordinal, so a numbered line carrying `0` is a **producer contract violation** (warn-once / assert; detail TBD).
- **Used when applying results:** the parser returns `N` source lines; instead of `document.lines[i]`, write the tokenized `CodeLine` to `document.lines[sourceToDoc[i]]`. This is exactly why the mapping is needed ("apply the colorized parser response back to the model").
- **No maintenance for now:** editing disassembly documents is out of scope (Q3), so the buffer is built at creation and not patched. Ordinary documents use `null` (identity) and need no mapping at all.
- **Character-offset mapping (source ↔ document):** intervals, scope graph, and usages use character offsets, so an offset map is required (Q6). Let `srcStart[i]` be the source char offset of source line `i` (`srcStart[0] = 0`; for `i < N-1`: `srcStart[i+1] = srcStart[i] + strLength(sourceToDoc[i]) + 1`) and `docLineStart(d) = document.getLineStartInd(d)`:
  - **No trailing newline (must match materialization):** the source `char[]` is built by joining lines with `\n` **between** lines only — `Document.getChars` / `getLineStartInd` insert no final newline. So the source has length `srcStart[N-1] + strLength(sourceToDoc[N-1])` (**no final `+ 1`**), and the `+ 1` in the recurrence applies **only for `i < N-1`**. Getting this wrong makes `docOffset` off by one at the tail.
  - **source → doc:** find the source line `i` containing offset `x`; `docOffset(x) = docLineStart(sourceToDoc[i]) + (x − srcStart[i])`.
  - **doc → source:** let `d = document.getLine(x).x`; if `d` is a source line (`sourceToDoc[i] == d`), `srcOffset(x) = srcStart[i] + (x − docLineStart(d))`; if `d` is a disassembly line, the offset has **no source equivalent** — callers snap to the **enclosing (predecessor) source line** (definition in Q6: greatest `i` with `sourceToDoc[i] < d`) and **clamp the in-line char to that line's length** (used only in viewport translation, Q8).

**Context:** the parser returns `N` **source** lines; `ParserUtils.updateDocument` currently replaces `document.lines[0..N)`.

**Closed detail (from Q6):** indexing is **not** redefined — disassembly lines remain separate document lines referenced by the parallel `sourceToDoc`; Q6 option (b) (attach-to-source-index) was rejected.

### 6. Shared coordinate space for Pos/tree/scope/usages — DECIDED (a)

**Decision:** Keep `usageToDef`/`defToUsages`, `IntervalTree`, `scopeGraph`, and viewport/reparse intervals in **source space** — exactly what the parser/library produces. Translate to **document space only when rendering/hit-testing** (interaction layer). Chosen to **reduce risk**: the structures stay **as the parser emits them** — no structure is rewritten. Only the **write/scatter path in `ParserUtils`** adapts (source-space loop guards, writes routed via `sourceToDoc` — see Q7); that work is mechanical and does not change the model.

**Why this stays low-risk:**
- **Rendering is content-based:** line/character coloring lives in each line's `CodeElement`s (written via `setLine`), not in the model structures — normal rendering does not need source→doc translation.
- **Positions are consulted only at interaction time:** goto-definition, find-usages, hover, code lens, folding look up `tree`/`usageToDef`/`scopeGraph` from a user action; translation happens there, in both directions.

**Hit-testing fast path (doc → source):** the `lineNumber`-based shortcut is valid only where the ordinal invariant (Q5) holds, i.e. when `sourceToDoc != null`: for a clicked document line `d`, `i = document.lines[d].lineNumber - 1`; sanity-check with `sourceToDoc[i] == d`. If the line is disassembly (no line number) or the check fails, fall back to a binary search over `sourceToDoc`. When `sourceToDoc == null` (identity), the reverse is simply `d` — the fast path never consults `lineNumber`. Reverse (source → doc) is a direct array read: `sourceToDoc[i]`.

**Position invariant (all model structures are source-space):** whenever `sourceToDoc != null`, every `Pos.line` **stored in or looked up from** `tree`, `usageToDef`, `defToUsages`, and `scopeGraph` is a **source line index** — never a document line. These structures are produced by the parser over source text and consumed as-is (this decision); nothing rewrites them. Building/looking up a `Pos` from a document `caretLine`/click line directly is the bug this invariant prevents — the map keys are source indices.

**Enclosing (predecessor) source line — definition:** for a disassembly document line `d`, its enclosing source line is the **greatest source index `i` with `sourceToDoc[i] < d`** (binary-search predecessor over the monotonic `sourceToDoc`) — i.e. the source line immediately **above** the disasm run. This is the one definition used by every "snap to the enclosing source line" below (Q5 offset math, Q7 reverse offsets, Q8 viewport anchor).

**Caret / click path (doc → source → lookup → doc — spell out):**
1. From the caret (or click) at document position `(d, c)`, compute the source line `s`: if `d` is a **source** line, use the `lineNumber` fast path `s = document.lines[d].lineNumber - 1` with the `sourceToDoc[s] == d` **sanity check**; if the check fails, fall back to binary search over `sourceToDoc` (Q8 helper). If `d` is a **disassembly** line there is no source row to map to:
   - **Click on a disasm row → skip the lookup** (attached lines have no usages/definitions/hover); do **not** synthesize a `Pos`.
   - For an unavoidable **line-level snap**, use the enclosing predecessor source line (definition above) and **clamp `c` to that line's length** (a disasm `c` can exceed the source line end).
2. Look up `Pos(s, c)` in the source-space structures (`usageToDef` / `defToUsages` / `tree` / `scopeGraph`) — only when step 1 produced a real source `(s, c)`.
3. Map every **result** line back through `sourceToDoc` **before** calling `Document.getCodeElement(Pos)` or navigating: `docLine = (sourceToDoc == null) ? result.line : sourceToDoc[result.line]` (bounds-check `result.line` against the source count, not `document.length()`).

`Model.computeUsages`, goto-definition, find-usages, hover, and code-lens all follow this exact path. (When `sourceToDoc == null`, every step is the identity and today's code is unchanged.)

**Consequence for Q7/Q8:** the parser's structures are consumed as-is (source space). Only the **apply path** adapts: `updateDocument`'s loop writes each parsed source line `i` into doc slot `sourceToDoc[i]` with source-space guards, and `updateDocumentInterval`'s splice conversions map the interval's source bounds to doc lines so results can be written into `document.lines` via `sourceToDoc`.

**Alternatives considered (rejected):**
- (b) Make the document index **source-only** and attach disassembly lines to source indices (rewrites the model index; more invasive).
- (c) Store disassembly lines with offset/fractional indices (ambiguous; discarded).

### 7. Applying parse results without clobbering disassembly — DECIDED

**Decision:** Line-level application is exactly the Q5 mapping: the parser returns `N` source lines; write parsed source line `i` to `document.lines[sourceToDoc[i]]` (identity when `null`). Writing through the mapping **cannot clobber** disassembly lines, because they are simply absent from the mapping.

**Residual details (the offset conversions are specified in the interval-apply step below; everything else is mechanical — nothing changes the model):**
- **Full apply (`ParserUtils.updateDocument`):** the loop writes via `sourceToDoc[i]`. The array-resize guard and the `saveOldLines` skip condition `i < documentLength` are today evaluated against the **document**, but with interleaved disassembly the loop iterates **source** lines — these guards must be evaluated in source space (with disasm, `lines.length` is already ≥ `N`, and skipping happens per source line). The freshly built `CodeLine`s must **preserve `lineNumber`** exactly as in the interval path (step 4 below — copy from the slot's previous line, or set the source ordinal); writing the default `0` would wipe the ordinals.
- **Interval apply (`ParserUtils.updateDocumentInterval`)** — spell out the mapping. `intervalStart/Stop` are char offsets in the **source-only** `char[]` the worker parsed; `srcStart[i]` is the cumulative source-line start table from Q5 (`srcStart[0] = 0`, `srcStart[i+1] = srcStart[i] + strLength(sourceToDoc[i]) + 1` for `i < N-1`; **no trailing newline after the last line** — Q5).
  1. **Locate the boundary source lines:** `s` = largest `i` with `srcStart[i] ≤ intervalStart` (binary search), in-line char `c = intervalStart − srcStart[s]`; likewise `e` / `c2` for `intervalStop`, with `srcStart[i] < intervalStop` since the stop is exclusive.
  2. **Translate to doc lines:** `docLeft = sourceToDoc[s]`, `docRight = sourceToDoc[e]`. The in-line chars `c`, `c2` are valid in the doc lines unchanged — disassembly only adds **lines** between source lines, it never mutates source line content, so the text inside line `s` is byte-identical in both spaces.
  3. **Boundary splices:** `left = document.lines[docLeft].getElementsToLeft(c)`, `right = document.lines[docRight].getElementsToRight(c2)` — the same calls as today, but on the mapped doc lines. Reparse boundaries always land on **source** lines, never on disassembly lines, so `docLeft`/`docRight` are never disassembly slots.
  4. **Write the `N` replacement lines:** for `i` in `0..N-1`, `document.setLine(sourceToDoc[s + i], new CodeLine(elements), success)` — **preserving `lineNumber`**: a fresh `CodeLine(elements)` would reset the field to the `0` default and destroy the source ordinal the inverse map (`lineNumber − 1`) and Q5's creation invariant depend on. Either copy `lineNumber` from the previous `CodeLine` occupying that slot, or set `line.lineNumber = s + i + 1` when writing through `sourceToDoc` (classic AUTO docs are fine either way — `0` stays correct). The worker's `N` source lines replace source interval `[s, s+N)`; each is scattered into its doc slot via `sourceToDoc`, so interleaved disassembly lines are never overwritten. Payload element offsets stay interval-relative, as today — no rebasing.
  5. **Tree/graph:** `tree.replaceInterval` and graph data keep **source-space** coordinates (Q6) — no offset translation at apply time.
- **v1 normative constraint for mapped documents (`N == e − s + 1`):** interval/viewport apply **requires the worker to return exactly the number of source lines it was sent** — `N == e − s + 1`, where `[s, e]` is the source interval sent. The mapping is built once and never patched (Q3/Q5), so `N != e − s + 1` (a **line insert/delete during apply**, i.e. a split/merge) would scatter parsed lines into wrong slots and silently corrupt source↔doc alignment. **Line insert/delete on apply is unsupported in v1.** If a mismatched `N` arrives, **abort the apply** — leave `document.lines` unchanged and log once; do not attempt to splice. Classic documents (`sourceToDoc == null`) keep today's insert/delete behavior unchanged.
- **Reverse (doc → source offsets)** is needed by interaction paths only: use `docOffsetToSrc` from Q5 — `d = document.getLine(x).x`; if `d` is a source line (`sourceToDoc[i] == d`) then `srcOffset = srcStart[i] + (x − docLineStart(d))`; if `d` is a disassembly line there is **no source equivalent** — callers snap to the **enclosing (predecessor) source line** (definition in Q6: greatest `i` with `sourceToDoc[i] < d`) with the in-line char clamped to that line's length (viewport translation, Q8).
- **`tree.replaceInterval`, `usageToDef`, `defToUsages`, `scopeGraph`:** remain in **source space** (Q6, decided) — no translation at apply time; the interaction layer translates on demand.
- **`setLine` semantic-token preservation** works unchanged (per doc slot).
- **Non-goal:** diff/undo/edit paths (Q10–Q12) are not adapted — source-only documents have `null` mapping and disassembly documents are never edited (Q3; editability derives from `!readonly && sourceToDoc == null && numbered`, line-numbers Q8).

**Context:** `ParserUtils.updateDocument` / `updateDocumentInterval` / `setLine(i, ..., success)` assume line `i` is a source line today; with the mapping they write to doc slots while preserving that assumption.

### 8. Viewport parsing with disassembly present — DECIDED

**Decision:** `Model.parseViewport` translates the widened visible **document** line range into a **source** range by **binary search over `sourceToDoc`** (the array is monotonic):

- `srcFirst = lowerBound(sourceToDoc, firstLine)` — first source line whose doc position `≥ firstLine`;
- `srcLast = upperBound(sourceToDoc, lastLine) - 1` — last source line whose doc position `≤ lastLine`;
- if `srcFirst > srcLast` (the viewport shows only disassembly lines) → **skip** the viewport parse.

That source range is what the fast parser receives (source-only payload, Q4). The three viewport ints (`getLineStartInd(firstLine)`, `getVpEnd(lastLine)`, `firstLine`) are replaced by their **source-space** counterparts over the source-only `char[]`. Widening by `VIEWPORT_OFFSET` is applied first; the policy is unchanged, only translated.

- **Avoid re-parsing unchanged ranges:** `parsedVps` must store the covered **source** interval, and `isVpParsed` runs on the same translated range. Unchanged source ranges are then not re-requested as the viewport scrolls across disassembly.
- **Anchor nuance (optional refinement):** if the first visible document line is a disassembly line, the binary search may exclude its **enclosing (predecessor) source line** (definition in Q6) just above the viewport. Including it (step back one source entry) keeps the visible disassembly tokens consistent.
- **Applying results back:** the returned source interval is mapped to doc slots via `sourceToDoc` (Q7); positions inside the model structures remain in source space (Q6).
- **Payload detail:** either keep sending the full source-only `char[]` with translated absolute viewport ints (minimal change), or send a rebased slice `[srcFirst..srcLast]` with enclosing tree intervals re-clipped. Chosen at implementation.

**Context:** `Model.parseViewport` computes `document.getLineStartInd(firstLine)` / `getVpEnd(lastLine)` / `getIntervals()` from visible document lines.

### 9. Incremental reparse vs disassembly insertion — DECIDED (not required for v1)

**Decision:** Incremental (iterative) reparse is **not required** when disassembly is present — in the first version a disassembly document is **always read-only**, so `Model.iterativeParsing` never fires for it:

- **Read-only contract — a hard gate, not warn-only:** any document with `sourceToDoc != null` (inline disassembly present) is **fully read-only**. Every **modifying** operation (insert/delete/backspace/typing/cut/paste/undo/redo/indent — any `Document` mutation) is **blocked at the model/edit gate whenever `sourceToDoc != null`**, for **all** lines — not merely on attached (non-numbered) lines. Numbered source lines in a mapped document are **not** editable either: the mapping is built once and never patched (Q3/Q5), so any edit would desynchronize source↔doc. This is the primary gate; the attached-line guard in line-numbers Q8 is a second line of defense (it only ever matters for a classic document that somehow holds attached lines, which itself implies `sourceToDoc != null`).
- **`EditorComponent.readonly` is the UI mirror, not the source of truth:** the authoritative condition is the **document's mapping** (`sourceToDoc != null`). `Document` owns that state (Q4). The **attach path** — whatever binds a `Document` to the editor (`EditorComponent.setModel` / `setDocument`) — mirrors it by calling `EditorWindow.setReadonly(true)` when it attaches a mapped document. The **JS descriptor factory** (Q2) only sets `sourceToDoc`; it does not touch the editor. Flow: factory sets `sourceToDoc` → attach mirrors it into `EditorComponent.readonly`. `readonly` is already enforced before cut/paste/undo today, so it remains the UI-level enforcement point.
- **Guard (warn once):** the warn-once fires **at that same attach point**, when a document with `sourceToDoc != null` is bound to an editor whose `readonly` is still `false` (i.e. the mirroring was skipped or a caller forced it off). It emits a **single warning per document** (not repeated). This is a **defense-in-depth log only** — enforcement does **not** depend on it (the model gate above does), and it must not be the sole safeguard against corrupting the built-once mapping.
- **Coordinates (if reparse is ever enabled later):** intervals are expressed in **source space** end-to-end — `document.tree.getReparseNode()` → sent interval → `replaceInterval` (Q6/Q7) — and line writes reuse Q7's mapping (`setLine(sourceToDoc[s + i], ...)`, preserving `lineNumber`). Recorded now so the later change is mechanical.
- **View-level disassembly changes never invalidate the tree:** no reparse is triggered for a purely view-level change (see Q10).

**Context:** `Model.iterativeParsing` uses `document.tree.getReparseNode()` and sends the interval plus `document.getChars()`.

## C. Versioning, diff, and editing

### 10. Versioning: which changes invalidate the parse? — DECIDED

**Decision:** View-level disassembly changes do **not** bump `document.currentVersion` — they must never force a reparse. In v1 this is largely moot: disassembly documents are read-only (Q9) and disassembly is built once at creation, so there are no post-creation view-level add/remove events at all. Folding is a view-layer concept and does not touch the parse version. `currentVersion` therefore advances only on **source edits**, exactly as today.

**Context:** `parseRes.version` must equal `document.currentVersion` to be applied.

### 11. Diff/sync/parse exclude disassembly; copy includes it — DECIDED

**Decision:** Two separate contracts, never conflated:

- **Copy includes disassembly:** a user copy copies **all selected text, disassembly included** — what is selected is what is copied. It operates on the **document** directly (doc space); no source↔doc translation.
- **Diff / sync / parse payload stay source-only:** `updateModelOnDiff`, `CpxDiff`, `syncEditing`, and the worker payload remain **source text only**. This holds structurally, not via per-API filters:
  - source-only documents have `null` mapping (no disassembly) → today's diff/sync path verbatim;
  - disassembly documents are read-only (Q9) → edits/diff/sync never fire for them (Q10/Q12).
- **Implementation note:** the worker payload keeps using the materialized **source-only** `char[]` (Q4) — a different path from user-facing copy, which reads the full document text (including disassembly). Keep `Document.getChars()` (document text, used by copy) distinct from the source materialization (used by the worker).

**Context:** `updateModelOnDiff`, `CpxDiff`, `syncEditing`, `Document.getChars()`/`getFullLength`, and copy operate over "the document".

### 12. Undo/redo — DECIDED

**Decision:** Disassembly insertions do **not** participate in undo/redo — they are derived/view data, not user edits. In v1 this is moot: disassembly documents are read-only (Q9), so no edits (and thus no undo history) occur on them; `UndoBuffer` is untouched. Ordinary documents have `null` mapping and their undo path is today's, verbatim.

**Context:** `UndoBuffer` records edits over the document.

## D. Rendering and numbering

### 13. Styling of disassembly `CodeElement`s — DECIDED

**Decision:**
- **Diff-mode look is NOT applicable** to disassembly documents: a diff model never exists for them (folding/diff build on the diff model — Q16), and disassembly documents are read-only (Q9).
- **`setSemanticTokens` never touches disassembly elements:** semantic tokens are produced from the **source text only** (they are never emitted for disassembly lines). On top of that, `Model.setSemanticToken` already rejects mismatches via `element.s.equals(token.text)`. The line must be translated **explicitly**: `docLine = (sourceToDoc == null) ? token.line : sourceToDoc[token.line]`. **Bounds-check `token.line` against the source count** (`sourceToDoc.length` when mapped; otherwise `document.length()`) — **never against `document.length()` alone**. With interleaved disassembly an LSP/source line index `< document.length()` can land on a disassembly row, and writing there would corrupt a non-source `CodeLine`. If `token.line` is out of source bounds, **drop the token** (defensive; the parser should not emit it). Today's `document.line(token.line)` must not be used unguarded.
- **Color scheme: DECIDED — run segments + a per-document token dictionary.** Disassembly lines are tokenized at **document construction**, not through the parser pipeline. An `ILineDescriptor` carries `tokens` (run segments: `{ text, tokenType? }`) instead of a single `content` string; `newTextModelFromLines(workers, lines, language?, uri?, tokenDictionary?)` accepts a **per-document token dictionary** (`{ [tokenType]: _SemanticTokenColorSettings }`, color settings via `_SemanticTokenLegendItem.color`). `JsTextModel.fromLines` splits each line into `CodeElement`s (one per run) — which also fixes the `element.s.equals(token.text)` elementization obstacle for attached lines — and collects a `SemanticTokenInfo` per colored run.
- **Applied through a dedicated document-token path, not `setSemanticTokens`.** Document tokens address **document lines directly** (attached lines have no source index), so they cannot go through the source-mapped `setSemanticTokens`. `Model.setDocumentTokens(...)` stores them and applies them via the shared `applyTokenAt` helper; because colors need the editor color scheme, application is **deferred until the editor attaches** (`setEditor` also calls it, so a model built before `editor.setModel` turns its colors on as soon as the editor is set). This keeps `setSemanticTokens` and its mapped-document tests **unchanged**.
- **Attached lines are the target; numbered (source) lines are best-effort.** The editor's job is to colorize source lines from the language parser, so a `tokenType` on a line that carries a `lineNumber` is only a hint. `ParserUtils.updateDocument` rebuilds every source `CodeLine` from the parser output and carries over only `lineNumber`; `Document.setLine` then copies the old element colors back **by position** when the element count is unchanged (it does not compare text), and semantic tokens later delivered by the language parser overwrite matching elements through `setSemanticTokens`. A caller color on a numbered line may therefore survive, may land on a different parser element, or may be dropped when the parser changes the split. Nothing re-applies it afterwards. Attached lines are outside `sourceToDoc`, so the parser never visits them and their colors live for the whole lifetime of the document (this is what the inline-disassembly sample actually colors).
- **Vocabulary is local to the demo.** The five disasm categories (instruction, register, numeric constant, `+`/`-` operator, size/keyword such as `DWORD`/`PTR`) are **not** added to `_SemanticTokenType` or `ParserConstants`: a run's `tokenType` is a free-form string resolved only through the document dictionary, so a new document can define its own names and colors. A run whose `tokenType` is not in the dictionary but names a **built-in** semantic type (e.g. `keyword`, `number`) still resolves via `ParserConstants.TokenTypes.getSemanticType`; a run without a `tokenType` stays plain default text.
- **Fallback / font style:** uncolored runs render as the scheme default; a dictionary entry may also set `background`, `italic` and `bold`, mapped to `SemanticTokenInfo.tokenStyle`.

**Context:** Which colors/styles do disassembly elements use? Does `setSemanticTokens` ever touch them? How do they look in diff mode?

### 14. Line numbers for disassembly — DECIDED

**Decision:** disassembly lines are **never numbered** (`lineNumber == 0`; not members of `sourceToDoc`); **no address column** — addresses (non-integer labels) go into `CodeElement` **content**, not the gutter and not a second gutter lane (see [line-numbers-refactoring-QA.md](line-numbers-refactoring-QA.md) Q5/Q12/Q13).

### 15. Numbering source lines when disassembly is present — DECIDED

**Decision:** The **disassembly producer (JS API)** assigns `lineNumber` at document creation, from the line descriptors (Q2) — and in a disassembly document it **is the 1-based source ordinal** (Q5 invariant), so `{1,-,-,2,3,-,4}` is exactly the descriptors' numbers. The source index buffer is built from those same descriptors (Q4/Q5), so numbering and source-ness come from one source of truth. **`0`/AUTO is never used for these lines** — source ordinals are explicit `≥ 1` (AUTO is a classic-document concept, see Q5 and line-numbers QA Q9).

- **Ordinary (non-disasm) documents are unaffected:** numbering follows line-numbers-refactoring-QA.md Q5/Q9 — display numbers with **no ordinal constraint**, and `lineNumber == 0` means **AUTO** (derive the document line index + 1), so documents that can be edited never renumber (editability derives from a null mapping + `editor.readonly` — line-numbers Q8/Q9; no producer fill, no edit-time maintenance).
- **Edits do not renumber:** editing documents that contain disassembly is out of scope (Q3); a future edit path would re-validate/re-assign numbers then, not now.
- **Folding does not renumber:** `lineNumber` is per-line display data; folding/compact-view mapping is a separate index, and display numbers persist (line-numbers QA Q5).

**Context:** when disassembly lines are interleaved, source lines must keep their **source** numbers (e.g. `{1,-,-,2,3,-,4}`).

### 16. Interaction with compact view / folding — DECIDED (out of scope; TBD)

**Decision:** Folding is built only on the **diff model**, and a diff model **never exists for disassembly documents** — so folding does not apply to them and is **out of the current scope** (TBD for a later version). `CompactCodeMapping` therefore only composes with the number provider for source-only documents (`null` mapping), where today's semantics are unchanged.

**Context:** `CompactCodeMapping` uses real document indices.

## E. Unified diff composition

### 17. Unified diff + inline disassembly — DECIDED (they do not compose in v1)

**Decision:** Inline disassembly and unified diff **do not compose** in the first version — they are **orthogonal line structures**:

- the **unified** view separates **docA/docB** (two documents);
- **inline disassembly** separates **doc/disasm** (one document plus attached disassembly lines).

A diff line never also carries inline disassembly in v1. Disassembly stays a read-only single-document presentation (Q9), and numbering never has to reconcile two disassembly sides.

**Context:** Unified diff interleaves lines from two documents; inline disassembly attaches to lines within one document.

### 18. Two-pane diff vs unified view — DECIDED

**Decision:**
- **Two-pane diff does NOT support disassembly in the first version** — neither side is a disassembly document.
- **Unified diff is also not a disassembly view:** its line separation is **docA/docB** (two documents), not **doc/disasm**. It is a later step and a **view-level interleave of already-tokenized documents** — it does not reuse the parser pipeline.

**Context:** Today two-pane diff uses `lineNumbers1`/`lineNumbers2` and separate `LineNumbersComponent`s; unified (single-pane) is a later step.

## F. Summary of the critical path

Most other questions depend on **Q1 (where disassembly lives)** and **Q6 (coordinate space)**.

- **Q1 is decided: (a) same `Document`.** Consequence: the parser only sees source, so its data lives in **source space** and Q4-Q9 are on the critical path.
- **Q2 is decided:** disassembly is supplied via a dedicated **JS API** that builds the document from an array of **line descriptors** (line number present ⇒ source line); the source index array is built there.
- **Q3 is decided (out of scope for now):** editing documents that contain disassembly is not handled; the index is built once at creation and not patched.
- **Q4 is decided:** the "source-only buffer" is an **index buffer** (document line indices, **not** a text copy); the worker payload is materialized from it. Source-ness is determined by **membership in the index**, and numbering coincides with it (numbered ⟺ member; no dedicated `hasLineNumber` flag is added — line-numbers Q9). **`null` means identity** (no disassembly lines), so ordinary documents need no mapping and no maintenance.
- **Q5 is decided:** store only the forward `sourceToDoc` buffer, built at creation; the inverse is derived from `CodeLine.lineNumber` **under the ordinal invariant** (`sourceToDoc != null` ⇒ `lineNumber` == 1-based source ordinal; display renumbering is disallowed in disasm documents). Used to apply parser results back; char offsets via the Q5 formula.
- **Q6 is decided (a):** model structures (`tree`/`scopeGraph`/`usageToDef`/`defToUsages`) stay in **source space**; `Pos.line` in them is **always a source index** when mapped. Translation to document space happens only in the render/hit-test (interaction) layer, via the explicit **doc → source → lookup → doc** path (`sourceToDoc` both ways). Hit-test doc→source uses the O(1) `lineNumber` fast path (ordinal invariant) with a `sourceToDoc[i] == d` sanity check; identity/null mapping reverse is just `d`.
- **Q7 is decided:** line-level application is the Q5 mapping (`setLine(sourceToDoc[i], ...)`, preserving `lineNumber`); interval/tree/graph offsets (Q8/Q9 wording above) are source-space and keyed on Q6. Mapped-doc apply is normative **`N == e − s + 1`** — line insert/delete on apply is unsupported; abort on mismatch.
- **Q8 is decided:** viewport → source range via **binary search over `sourceToDoc`** (monotonic); no visible source ⇒ skip parse; `parsedVps` stores source intervals to avoid re-parsing.
- **Q9 is decided:** incremental reparse is **not required** when disassembly is present — disasm documents are **hard read-only**: modifying ops are blocked at the model gate whenever `sourceToDoc != null` (all lines, not just attached), with `EditorComponent.readonly` the UI mirror set at attach; **warn once** (defense-in-depth) if a non-RO editor attaches a disassembly document.
- **Q10 is decided:** view-level disassembly changes never bump `document.currentVersion`; version advances only on source edits (as today).
- **Q11 is decided:** **copy includes disassembly** (all selected text); diff/sync/parse payload stay source-only — structurally guaranteed by RO disasm docs (Q9) + `null` mapping on editable docs.
- **Q12 is decided:** disassembly insertions do not participate in undo/redo (derived view data; moot while disasm docs are RO).
- **Q13 is decided:** diff-mode look not applicable (no diff model for disasm docs); `setSemanticTokens` never touches disasm elements (source-only tokens + `element.s.equals(token.text)` guard), and it maps `token.line` via `sourceToDoc` with a **source-count** bounds check (never `document.length()` alone); disasm colorization is done at document construction via descriptor **run segments** + a per-document **token dictionary**, applied through the dedicated `Model.setDocumentTokens` path (deferred until the editor attaches) so `setSemanticTokens` stays unchanged.
- **Q14 is decided:** no address column — non-integer labels go into `CodeElement` content.
- **Q15 is decided:** numbers are assigned by the disassembly producer (JS API) at creation; `lineNumber` is the 1-based source ordinal (Q5 invariant); `0`/AUTO is never used on numbered lines in a disassembly document (classic-document concept only — line-numbers Q9); edits/folding never renumber (Q3, per-line display data).
- **Q16 is decided (out of scope, TBD):** folding builds on the diff model, which never exists for disasm documents; folding is out of the current scope.
- **Q17 is decided (no composition in v1):** inline disassembly and unified diff do not compose — unified separates **docA/docB**, inline disasm separates **doc/disasm**; a diff line never carries disassembly in v1.
- **Q18 is decided:** two-pane diff does not support disassembly in v1; unified diff is a later docA/docB view-level interleave of already-tokenized documents (no parser pipeline).
- If Q1 were revisited to (b)/(c) (separate layer or second document), the parser pipeline would stay mostly untouched and the work would concentrate in the view/interleave and numbering layers.
